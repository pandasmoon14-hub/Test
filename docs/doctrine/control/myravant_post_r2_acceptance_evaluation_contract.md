## 1. Purpose and authority boundary

PR2-TEST expands executable acceptance and adversarial evaluation of
already accepted Myravant invariants. It evaluates accepted owners; it
does not absorb their semantic authority.

Central law:

> Evaluation may demonstrate, falsify, or expose compliance; it may not create the authority, mechanic, world fact, or semantic rule being evaluated.

Tests do not invent missing doctrine. A failing test does not gain
authority to define the missing rule. Benchmark results do not create
authority. Evaluation infrastructure does not gain semantic ownership
merely because it observes, measures, replays, stores, or compares
authoritative evidence.

PR2-TEST authorizes no runtime implementation, production-schema
implementation, PR2-IMPL activation, R4-B activation, R4 activation,
runtime promotion, canon promotion, source conversion, or native-content
promotion.

## 2. Game-led posture

PR2-TEST protects playable capability rather than maximizing governance
artifacts or raw test count.

Preferred flow:

`accepted invariant -> executable pressure -> observable result -> deterministic evidence -> failure classification -> regression protection`

Material failures route:

`preserve -> reproduce -> classify -> route to existing owner -> repair if separately authorized -> regression test`

A failure does not automatically justify a new manager, semantic owner,
generalized subsystem, doctrine family, distributed infrastructure, or
permanent gameplay restriction.

Existing executable evidence should be reused before duplicate coverage
is added. Test-count growth is not an objective. No arbitrary test-count
quota defines completion.

The immediate successor activity inside PR2-TEST is a bounded executable
gap assessment across the seven evaluation families. It must not restart
repository-wide doctrine discovery.

## 3. Initial evaluation families

The activation defines exactly seven evaluation families:

1. `source_governance`
2. `originality_and_information_barrier`
3. `deterministic_topology_equivalence`
4. `persistence_replay_and_recovery`
5. `fidelity_aggregation_and_reconstitution`
6. `overload_backpressure_and_lawful_degradation`
7. `failure_isolation_and_authority_ambiguity`

These are evaluation families, not semantic owners, services, managers,
or runtime subsystems.

## 4. Source-governance pressure

Evaluation should demonstrate that:

- provenance remains attributable;
- research evidence does not become canon automatically;
- historical or research-only surfaces do not become runtime authority;
- source-local assumptions do not become Myravant defaults by repetition.

## 5. Originality and information-barrier pressure

Evaluation should demonstrate that:

- source analysis remains separated from Myravant-native design;
- renaming, paraphrase, translation, or numeric alteration is not treated
  as independent originality by itself;
- quarantined or ineligible material does not silently become eligible;
- source-aware analysis does not leak protected source expression into
  Myravant-facing production surfaces.

## 6. Deterministic topology-equivalence pressure

Where accepted runtime capability exists, evaluation should pressure:

- worker-count independence;
- physical-completion-order independence;
- deterministic authoritative ordering;
- partition-boundary equivalence;
- partition migration;
- cross-partition interaction.

Physical topology may affect throughput. It may not silently change
authoritative meaning.

## 7. Persistence, replay, and recovery pressure

Evaluation should pressure:

- reconstruction from committed evidence;
- snapshots;
- replay equivalence;
- crash recovery;
- corruption detection;
- duplicate events;
- stale commands;
- committed-randomness preservation.

Committed randomness outcomes are evidence-bearing history and must not
be rerolled merely because replay, retry, overload, migration, or
recovery occurs.

## 8. Fidelity, aggregation, and reconstitution pressure

Evaluation should pressure:

- detailed-to-aggregate transitions;
- aggregate-to-detailed transitions;
- committed-fact preservation;
- unresolved-detail preservation;
- background/foreground cycling;
- repeated fidelity cycles;
- lawful materialization.

Evaluation does not authorize PR2-FID semantics to be rewritten.

## 9. Overload, backpressure, and lawful degradation pressure

Evaluation should pressure:

- bounded queues;
- admission pressure;
- deferred work;
- hotspots;
- retry storms;
- lawful degradation;
- recovery after overload.

Operational pressure must not rewrite logical time, legality,
authoritative order, committed facts, hidden-information boundaries, or
version applicability.

## 10. Failure-isolation and authority-ambiguity pressure

Evaluation should pressure:

- worker or partition failure;
- message loss;
- duplicate delivery;
- stale reads;
- incomplete persistence;
- replay disagreement;
- split-brain authority risk;
- authority ambiguity.

Authority ambiguity must fail closed or remain explicitly unsupported.
Evaluation must not fabricate an authority owner to force a passing
result.

## 11. Player freedom pressure

PR2-TEST should increasingly include fictionally coherent unusual
actions. Evaluation must not assume that all lawful play maps to a closed
verb menu.

Where existing capability permits, pressure should route attempts
through the meaningful distinctions among:

- intent;
- method;
- capability;
- resources;
- relationships;
- target;
- opportunity;
- environment;
- consequence;
- deterministic resolution.

Failure to represent an unusual action should expose a real capability
gap rather than be hidden behind an invented permanent command
restriction.

## 12. Persistent-world pressure

Where existing runtime capability permits, evaluation should pressure:

- session boundaries;
- stable identity;
- persistent consequences;
- reload and recovery;
- protagonist-independent continuity;
- delayed effects;
- lawful off-screen state;
- return to previously affected people and places.

PR2-TEST does not implement missing persistent-world mechanics.

## 13. Evidence and failure routing

A material finding should preserve enough evidence to determine the
repository state, active rule/version context, initial state, stimulus,
expected behavior, actual behavior, first divergence where known, and
reproduction status.

The preferred disposition is:

`failure -> evidence -> reproduction -> classification -> existing owner -> separately authorized repair -> regression`

An evaluation failure is not itself implementation authority.

## 14. Initial completion posture

PR2-TEST remains active while material accepted post-R2 invariants still
lack adequate executable regression or evaluation coverage.

Completion requires a bounded evidence-based determination that material
post-R2 invariants have executable protection, or an explicit lawful
handoff for gaps that belong to future implementation rather than this
evaluation workstream.

Completion is not defined by:

- a raw number of tests;
- doctrine-document count;
- benchmark volume;
- repository-wide rediscovery;
- implementation of missing mechanics.

PR2-IMPL remains separately blocked and requires its own owner
authorization. R4-B remains unauthorized. Runtime promotion remains
uncleared.
